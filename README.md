# IBSolver

Етап 4: настільний застосунок для Windows 10/11 на Go, Wails v2 та SQLite.
Український інтерфейс, темна тема, кілька конфігурацій і Canvas-графік до шести
часових рядів. Незалежне чисельне ядро та робочий математичний приклад осцилятора.

## Запуск

Потрібні Go 1.27.1+, Wails CLI 2.16.0, Node.js/npm та WebView2. Наявне середовище
перевіряється командою `wails doctor`. Початковий каркас створено офіційною
командою `wails init -n IBSolver -t vanilla`.

```powershell
cd D:\go\ibsolver
wails dev
```

Збірка: `wails build -trimpath`; готовий застосунок — `build\bin\IBSolver.exe`.
Для відтворюваного встановлення frontend-залежностей: `cd frontend; npm ci`.
Якщо sandbox не дозволяє запис у стандартні кеші, перед командами встановіть
`$env:GOCACHE="$PWD\.cache\go-build"` та
`$env:npm_config_cache="$PWD\.cache\npm"` з кореня репозиторію.

## Робота і збереження

- Нова конфігурація створюється кнопкою «Нова». Валідні зміни назви, параметрів
  осцилятора, інтегратора та DEMO автоматично записуються через 450 мс після введення. Кнопка
  «Зберегти» явно підтверджує запис. Дочекайтеся позначки «Збережено» перед закриттям.
  Незавершені або некоректні значення не замінюють останні збережені параметри.
- «Розрахувати» інтегрує `x′ = v`, `v′ = −(k/m)x − (c/m)v`: маса m у кг,
  жорсткість k у Н/м, опір c у кг/с, початкові x₀ у м та v₀ у м/с, час у с.
  Це математичний приклад, не спеціалізований інженерний розрахунок.
  Шість рядів: x, v, прискорення, кінетична, потенціальна й повна енергія у Дж.
  Панель ліворуч містить кінцеві значення, енергії, статистику та знімок параметрів.
  Bridge виконується асинхронно; «Скасувати» перериває інтегрування. Помилка або
  скасування залишають попередній успішний результат.
- Явний перемикач режиму показує лише активні поля DEMO або осцилятора.
  Перемикання зберігає обидва набори параметрів; перевіряється лише активний.
- «Створити DEMO» в режимі DEMO генерує шість математичних рядів, зберігає їх транзакційно й
  лише після успішного запису показує новий результат. DEMO не є фізичним розрахунком.
- Перемикання конфігурацій і повторний запуск відновлюють збережені числові дані
  без генерації рядів. Зміна параметрів залишає попередні результати та позначає їх.
- Усі криві відображаються на одному полі зі спільною часовою віссю. Легенда
  над графіком керує видимістю та окремим масштабом кожної кривої (0,1…10).
  Вертикальна шкала нормалізована: `y / опора × масштаб`, у межах −1,25…1,25;
  опора — явне додатне значення з метаданих (Reference), а за його відсутності —
  `max(abs(y))` (Automatic; для нульового ряду — 1). Нові DEMO-ряди мають опори
  за заданими амплітудами; старі результати зберігають Automatic. Нормалізація та
  масштаб не змінюють числових даних;
  значення поза цими межами обрізаються. Курсор показує вихідні значення
  найближчої спільної часової точки у власних одиницях кожної величини.
- Ширина результатів змінюється перетягуванням роздільника або стрілками клавіатури,
  коли роздільник у фокусі. Видимість і масштаби зберігаються за стабільними ID серій, ширина — глобально.
- «Відновити з БД» повторно завантажує робочий стан. Пошкоджений або несумісний
  результат пропускається з повідомленням; параметри залишаються доступними.

База: `%APPDATA%\IBSolver\ibsolver.db` (`os.UserConfigDir`). Міграції використовують
`PRAGMA user_version`; новіші невідомі схеми відхиляються без зміни. Таблиці:
`configurations`, `runs`, `run_series`, `app_settings`. Ряди — один gzip JSON BLOB
на запуск; параметри конфігурації та незмінний знімок запуску зберігаються окремо.
Міграція v2 додає JSON-параметри чисельного прикладу та окремий знімок запуску,
зберігає таблиці, DEMO-параметри, старі запуски й налаштування v1. Відсутні
чисельні параметри старих конфігурацій отримують стандартні значення в пам'яті.
Stage 3 залишає SQL-схему v2: чинні JSON-поля містять версіонований контейнер
`format: 1`, явний режим і типізовані параметри. Старі формати читаються окремо,
без перезапису рядків і BLOB. Для старої конфігурації без явного режиму валідні
параметри осцилятора означають Oscillator, інакше DEMO, незалежно від останнього
запуску. Це детерміноване правило сумісності, а не точне відновлення історично
активного режиму. Режим знімка запуску визначає його версія результату. Останній ID запуску
обчислюється за наявними зв'язками таблиць, додаткова таблиця не потрібна.
Знімок нового запуску містить лише активні параметри. Старим серіям ID додаються
в пам'яті, опорні значення не вигадуються. Позиційні налаштування переносяться
на ID під час завантаження і записуються наступним збереженням налаштувань.
Версії `demo-v1` та `oscillator-rk45-v1` перевіряються незалежно.
База, кеші, залежності та результати збірки виключені з Git.

JSON-обмін зберігає назву, режим та всі набори параметрів у UTF-8
(`format: "ibsolver-configuration"`, `version: 1`). Імпорт перевіряє всі набори
та створює нову конфігурацію; ліміт — 1 МіБ. ID, налаштування та результати
не експортуються. Невідомі поля й версії відхиляються.
CSV містить усі вихідні серії останнього збереженого запуску з одиницями та
точністю float64, незалежно від видимості, масштабів і поточних параметрів.
Колесо масштабує час біля курсора (до 1000×), перетягування зсуває діапазон;
подвійний клік або «Увесь графік» повертає повний діапазон. Дані не змінюються.
Нові запуски зберігають назву на момент запуску; для старих показано поточну назву.

## Чисельний метод

`internal/ode` — Dormand–Prince RK45, явна вкладена пара 5(4) для нежорстких ODE,
без нових залежностей. Вкладена оцінка дозволяє адаптувати крок без окремого
подвоєного інтегрування. Коефіцієнти: Dormand & Prince (1980),
[DOI](https://doi.org/10.1016/0771-050X(80)90013-3);
звірено з [реалізацією SciPy](https://github.com/scipy/scipy/blob/main/scipy/integrate/_ivp/rk.py).
Прийняття кроку: максимум компонентних відношень локальної оцінки похибки до
`atol + rtol·max(|y_old|, |y_new|)` не перевищує 1. Це не гарантія глобальної похибки.
Скалярний абсолютний допуск діє окремо в одиницях кожної компоненти (для прикладу
м та м/с); відносний — безрозмірний.

Підтримуються довільний ненульовий розмір стану, float64, context cancellation,
типізовані помилки, перевірки скінченності та ліміт усіх спроб кроку. Час зростає;
зворотне інтегрування, stiff-методи, події та dense output не реалізовані.
На кожну вихідну точку виконується справжній крок без інтерполяції; його залишок
може бути меншим за мінімальний крок, але все одно мусить пройти оцінку похибки.
Частота точок графіка впливає на кроки та вартість. Жорсткі або надмірно вимогливі
задачі можуть завершитися помилкою кроку чи ліміту; частковий запуск не зберігається.

## Структура і залежності

- `internal/domain`: типи й перевірки без Wails/SQLite.
- `internal/application`: координація сценаріїв і послідовність записів.
- `internal/storage/sqlite`: параметризований SQL, міграція, транзакції, відновлення.
- `internal/chartdata`: DEMO-генерація та адаптер математичного прикладу.
- `internal/ode`: незалежний інтегратор; `internal/chartdata/oscillator.go`:
  модель осцилятора та перетворення інтегрованого стану на часові ряди.
- `app.go`: тонкий Wails API; `frontend/src/chart.js`: незалежний Canvas-компонент.
- Wails v2 — настільне вікно й Go/JS bridge; `modernc.org/sqlite` — SQLite без CGO;
  Vite — стандартний toolchain офіційного Vanilla JS шаблону. UI/chart frameworks та ORM відсутні.

Workspace: `D:\go\ibsolver.code-workspace` містить Source і References.
`D:\go\ibsolver-refs` використовується лише для читання і не є репозиторієм.
Перелік джерел — [docs/SOURCES.md](docs/SOURCES.md).

## Перевірка

`go test ./...` перевіряє аналітичні розв'язки, фізичні інваріанти осцилятора,
скасування, граничні випадки, SQLite-міграцію v1→v2, перезапуск, незмінність знімків і точне
відновлення рядів, налаштування, пошкоджені результати та відкат невдалого запису.
Frontend: `npm test` перевіряє нормалізацію та налаштування за ID; `npm run build` у `frontend` (після генерації bindings командою Wails).
Повна desktop-збірка: `wails build -trimpath`.

Для Stage 1 також виконано native smoke у власному тестовому профілі: DEMO,
автозбереження, курсор, масштаби та відновлення після перезапуску з незмінною
контрольною сумою рядів. Перевірено native-розміри вікна 800×560 і 1280×800.
Для автоматизації використано окрему діагностичну збірку з локальним портом
WebView2; робочий `IBSolver.exe` його не відкриває.

Для Stage 2 також перевірено native Wails/WebView2 у власному профілі: кнопка
розрахунку, шість кривих і курсор, помилка ліміту та скасування зі збереженням
попереднього результату. Після перезапуску ID запуску, SHA-256 числових рядів,
параметри й підсумки залишилися незмінними. Перевірено вікна 800×560 і 1280×800
(клієнтські області 786×523 та 1266×763 CSS px у тестовому середовищі).

Тест `TestAnalyticalSolutions`: 0…20 с, 41 вихідна точка, rtol = 1e-3, 1e-6,
1e-9; atol = rtol·1e-3. Зменшення допусків зменшило максимальну абсолютну похибку
компонент стану. За rtol=1e-9 отримано такі округлені верхні значення:

| Задача | max abs похибка x | max abs похибка v |
| --- | --- | --- |
| Згасання (безрозмірний стан) | 7,69e-11 | — |
| Гармонічний осцилятор | 3,29e-9 м | 7,31e-9 м/с |
| Затухаючий осцилятор | 3,72e-10 м | 7,07e-10 м/с |

Це результати конкретних тестів, а не універсальна гарантія. `TestOscillatorPhysics` перевіряє
незатухаючий, недокритичний, критичний і надкритичний режими, баланс сил, суму
енергій, збереження енергії без опору та спадання за наявності опору.

Історичні BAS/XLS та спеціалізовані моделі в Stage 2 не досліджувалися й не переносилися.
