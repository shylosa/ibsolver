# IBSolver — Stage 6A: контракт постійного редактора

## 1. Purpose & Scope

Статус: **проєкт для погодження, реалізацію не дозволено цим документом**.
База: Stage 5, `5cd87d5adcb453df1fe887a51d401e2d90b52e54` (HEAD перевірено).
Мета наступного окремого завдання — введення, збереження та JSON-обмін
підготовчими даними без спеціалізованих обчислень.

Джерело фактів — [LEGACY_SPEC.md](LEGACY_SPEC.md), §4–5; архітектури — §8
і перелічений у §9 цього документа поточний код. `X` нижче означає оригінал
[Диплом.xls](../../ibsolver-refs/Диплом.xls), аркуш `Расчеты`.
Адреси комірок — точні локатори першоджерела, зафіксовані Stage 5;
повторне читання BAS/XLS для цього контракту не виконувалося.

**Факти:** `Confirmed` — прямо встановлено джерелом; `Probable` — інтерпретація;
`Unknown` — свідчень недостатньо. Усі ID, українські підписи, компонування,
числовий формат зберігання та поведінка нижче — **рекомендації**, а не історичні
правила. До погодження §10 вони не є затвердженим контрактом реалізації.
Перенесення формул, довідників, solver, імпорт BAS/XLS та автоматичний зв'язок
XLS → BAS не входять до обсягу. Наявні DEMO й Oscillator зберігаються.

## 3. Field Contract

Сім предметних полів; наявна назва конфігурації до цієї кількості не входить.
ID нижче — ключі нового блока `parameters.preparation`, без ототожнення
`d/q/ns/f1/af` з подібними іменами BAS. Підпис «Параметр» навмисно не додає
непідтвердженого фізичного тлумачення. Пояснення ролі — у довідці за локатором.

| Field ID | Label | Legacy name | Group | Type | Storage unit¹ | Display unit | Required | Default | Validation² | Source | Confidence³ |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| d | Параметр d | d | Вихідні дані | Number | м¹ | мм | Unknown | Unknown | Unknown | X: C7, D7, E7 | Confirmed |
| q | Параметр q | q | Вихідні дані | Number | кг | кг | Unknown | Unknown | Unknown | X: C8, D8, E8 | Confirmed |
| vd | Швидкість Vд | Vд | Вихідні дані | Number | м/с | м/с | Unknown | Unknown | Unknown | X: C9, D9, E9 | Confirmed |
| lc | Параметр lc | lc | Вихідні дані | Number | м | м | Unknown | Unknown | Unknown | X: C10, D10, E10 | Confirmed |
| ns | Коефіцієнт ns | ns | Вибрані коефіцієнти | Number | Unknown | Одиницю не встановлено | Unknown | Unknown | Unknown | X: G7, H7 | Confirmed; unit Unknown |
| f1 | Коефіцієнт f1 | f1 | Вибрані коефіцієнти | Number | Unknown | Одиницю не встановлено | Unknown | Unknown | Unknown | X: G8, H8 | Confirmed; unit Unknown |
| af | Коефіцієнт af | af | Вибрані коефіцієнти | Number | Unknown | Одиницю не встановлено | Unknown | Unknown | Unknown | X: G9, H9 | Confirmed; unit Unknown |

¹ Одиниця джерела для `d` — **мм**; зберігання в **м** є пропозицією SI,
а не властивістю XLS. Для решти трьох відомих одиниць пропонується зберегти
одиницю джерела. Правило перетворення визначене в §4; рішення D3.
² Тут лише предметні обмеження: допустимий знак, діапазон, зв'язки між полями
не підтверджені. Загальні технічні перевірки чисел — окремо в §6.
³ Confirmed стосується позначення, ролі Input, типу Number та явно підписаної
одиниці джерела; не засвідчує запропоновані ID, підписи, групування чи SI-storage.

Підтвердження ролі всіх семи входів: X: K6; D7:D10 і H7:H9 — жовті
числові літерали, заголовки груп C6/G6. Експоненційний формат D8
підтверджує спосіб відображення, але не допустимий діапазон або точність.

**Недостатність даних:** для `ns`, `f1`, `af` неможливо безпечно реалізувати
введення з фізично визначеною одиницею до уточнення. D2 пропонує дозволити
лише збереження числового значення джерела з постійним попередженням,
без конвертації та використання в обчисленнях. Для всіх семи полів фізична
валідація й розрахункова готовність залишаються невизначеними.

Облік невизначеностей: **3 одиниці**; для **7 полів** невідомі Required,
Default і предметні обмеження — **21 позиція метаданих у трьох категоріях**,
а не 21 встановлене правило. Нові поля починаються порожніми, без defaults;
це стан відсутності, а не припущене початкове число. Значення прикладів
не переносяться. F72:F74 (`W0`, `pm`, `LS`) — формульні Output, а не поля;
довідникові таблиці й службові змінні BAS виключені (LEGACY_SPEC §4–6).

## 4. Units Policy

| Рівень | Запропоноване правило |
| --- | --- |
| Внутрішнє числове представлення | JS Number / Go float64 (IEEE 754 binary64), лише скінченні значення; це не одиниця вимірювання і не гарантія десяткової точності |
| Зберігання | Типізований блок; одиниці закріплені контрактом його полів: `d` у м, `q` у кг, `vd` у м/с, `lc` у м; три Unknown зберігаються без масштабування |
| Введення | Одиниці джерела: мм, кг, м/с, м; довільного перемикача одиниць немає |
| Відображення | Ті самі одиниці, що при введенні, видимі біля кожного значення; довідка для `d` пояснює SI-storage |

Для відомого `d` на межі UI ↔ domain пропонується точний за визначенням
коефіцієнт: `storage_m = input_mm / 1000`, показ — зворотне масштабування.
Його обчислення в binary64 має звичайну похибку представлення. Перетворення
виконується один раз при прийнятті зміни, не під час кожного render;
повторне відкриття/збереження без редагування не змінює числове значення.
Це контракт майбутньої реалізації; Stage 6A конвертацію не реалізує.

Для Unknown показувати **«Одиницю не встановлено»** біля поля, а в help —
«Числове значення джерела; фізичну одиницю не підтверджено». Не показувати
«безрозмірне», SI або «ум. од.». Не застосовувати до XLS загальну SI-примітку
з BAS. Не виводити одиниці чи залежності коефіцієнтів зі схожості імен.
JSON містить канонічні значення, без локалізованих рядків та одиниць у числах;
семантика одиниць визначається версією контракту (§9).

## 5. UI Layout

Зберегти одне темне україномовне вікно Stage 4, верхню область параметрів,
лівий регульований стовпчик результатів, Canvas, JSON і CSV та zoom/pan
для наявних результатів. Не додавати майстра, вкладених вкладок чи бібліотек.
Пріоритет чотирьох основних входів — UX-рекомендація, а не фізичний рейтинг.

```text
Заголовок: IBSolver · Відновити з БД
Конфігурація · Режим · Назва · Нова · Імпорт JSON · Експорт JSON
Вихідні дані: [d | мм] [q | кг] [Vд | м/с] [lc | м]
▸ Вибрані коефіцієнти (3; одиниці не встановлено)
  [ns | одиницю не встановлено] [f1 | ...] [af | ...]
Зберегти · стан збереження · Розрахувати (недоступно) · пояснення
Результати (регульовані) │ розділювач │ графік / порожній стан
Статус / помилка
```

Додаткова група початково згорнута; помилка в ній розгортає групу, фокусує
поле, не стирає текст. Підписи, одиниці та помилки доступні з клавіатури;
довгі пояснення — у help, доступному також через фокус, не лише hover.
Незаповнене поле: нейтральне «Не задано». Некоректне: текст помилки й
`aria-invalid`, без залежності лише від кольору. Невідома одиниця — окреме
попередження, не parse error. Tab проходить видимі поля, Enter виконує «Зберегти».

Концептуальна перевірка місткості (бюджети в CSS px, **не native-перевірка**):

| Розмір вікна | Верх і поля | Робоча область |
| --- | --- | --- |
| 800×560 | Панель конфігурації переноситься на два рядки; чотири основні поля в одному рядку, коефіцієнти у двох колонках. Область параметрів прокручується окремо, до 40% доступної висоти | За зовнішніх відступів 24 px: 776 − 240 − 7 = 529 px для графіка з типовою панеллю; навіть 480 px лишає 289 px. При умовному резерві 88 px на заголовок/статус і 224 px на параметри лишається 248 px робочої висоти |

Довгі підписи Unknown переносяться всередині комірки без обрізання вводу.

viewport верхній scroll має зберегти доступ до дій і видиму робочу область;
горизонтального прокручування всього вікна бути не повинно.

## 6. Input & Validation Behavior

**Parsing** визначає числове значення тексту. **Validation** перевіряє
підтверджений предметний контракт і технічну скінченність; відсутність
відомої заборони не є підтвердженням фізичної допустимості. **Readiness**
визначається операцією: збереження/JSON допускають неповну конфігурацію
за D2/D4, розрахунок у цьому режимі завжди недоступний.

Пропозиція парсера: текстові поля, повний розбір рядка, без `parseFloat`
із прийняттям префікса. Прибрати лише крайові пробіли; приймати десяткову
кому **або** крапку, необов'язковий знак та `e/E` з цілим показником зі знаком.
Мантиса має хоча б одну цифру; дозволені `0,5`, `.5`, `1.5e-3`.
Рядок із кінцевим десятковим роздільником (`1,`), `-`, `+`, `1e`, `1e-`
вважається незавершеним. Це нова UX-політика, не виявлене правило Excel.

| Випадок | Пропонована поведінка |
| --- | --- |
| Порожнє поле | Прийняти як відсутнє значення (`nil` / JSON `null`), не як 0; зберігати за D4 |
| Нуль | Окреме числове значення; технічно зберігати, фізичну допустимість не стверджувати |
| Від'ємне | Розбирати й зберігати за відсутності підтвердженої заборони; попередження про неперевірені предметні межі |
| Дробове | Приймати; жодне з семи полів не доведено як Integer або Selection |
| Експоненційне | Приймати завершений запис; формат D8 — свідчення відображення, не меж |
| Дуже велике/мале | Перевірити результат розбору та конвертації. Overflow, а також ненульова десяткова мантиса, що перетворилася на 0 через underflow, — технічна помилка; скінченне ненульове значення, включно з subnormal, приймати без довільного предметного ліміту |
| Частково введене | Зберегти raw text у чернетці; не замінювати останнє коректне число. Після blur/«Зберегти» пояснити «Завершіть число» |
| Некоректний роздільник | Два роздільники, змішана кома/крапка, внутрішні пробіли, розділювачі тисяч, одиниці в рядку — помилка; не вгадувати значення |
| NaN/Infinity | Відхилити на UI й Go-рівні, включно з нескінченністю після конвертації |
| Поза підтвердженими межами | Якщо такі межі будуть окремо затверджені — помилка біля поля, без clamp. Зараз жодного числового предметного min/max немає |
| Required Unknown | Не показувати зірочку required; пояснювати, що обов'язковість для обчислення не встановлена. Це не зміна статусу Unknown на No |

Не округлювати до масок XLS, не обмежувати довільно кількість знаків.
Зберігати binary64 з round-trip JSON; точний первісний десятковий текст
після перезапуску не гарантується. Рекомендація потребує D4.
Помилка parsing не має переходити до SQLite, а Go повторно перевіряє типи,
скінченність і підтверджені обмеження, не довіряючи лише UI.

## 7. Autosave & State Transitions

Наявна основа: `frontend/src/main.js` — `revision`, `draftQueue`, debounce
**450 мс**, `autosave`, `operation`; `SaveConfiguration` атомарно записує
конфігурацію й Settings, а не Run. Нижче — бажаний контракт із потрібними
доповненнями, а не твердження, що всі ці гарантії вже реалізовано.

- Розділити raw draft полів, останній підтверджений SQLite-стан і локальну
  ревізію. `input` змінює draft, не відтворює форму зі State відповіді.
- Завершена коректна конфігурація, включно з явним очищенням до `null`,
  потрапляє до послідовної черги через 450 мс без нових змін. Якщо хоча б
  одне поле незавершене/некоректне, не зберігати **всю поточну ревізію**;
  попереднє збереження й raw text залишаються. Так немає прихованого
  часткового запису інших полів. Раніше відправлений коректний знімок може
  завершитися, але не означає, що новішу чернетку збережено.
- Запити містять незмінний знімок конфігурації/Settings, прив'язаний локально
  до ID та ревізії. Відповідь підтверджує лише відповідну ревізію; старіша
  не підміняє новіший текст, активну конфігурацію чи Settings. Записи
  конфігурацій і налаштувань серіалізувати спільно, щоб старий знімок Settings
  не повертав попередню активну конфігурацію чи ширину панелі.
- Стан: «Є незбережені зміни» → «Збереження…» → «Збережено» лише після
  успіху актуальної ревізії. При SQLite-помилці: «Не збережено» з причиною,
  чернетка лишається; «Зберегти» повторює запит, без нескінченних повторів.
- «Зберегти» негайно запускає ту саму перевірку та flush без очікування
  debounce, очікує завершення запису; не створює копії, Run або експорту.
  Некоректний draft лишається з поясненням. Без змін і помилок кнопка недоступна.
- Перемикання конфігурації/режиму, «Нова», «Відновити з БД», імпорт і закриття
  спершу завершують коректний pending-save. Для незавершеного draft або
  помилки запису перехід зупиняється: «Повернутися до редагування» або явне
  «Відкинути незбережені зміни». Друге відкидає лише draft після завершення
  вже відправлених записів; не скасовує виконаний commit. При скасуванні
  переходу селектор повертається до попереднього значення. Для закриття
  потрібен відповідний Wails lifecycle guard, а не асинхронний save в unload.
- JSON export дозволений лише після успішного flush актуальної коректної
  ревізії; незавершений draft не підміняється старим експортом без пояснення.
  Для імпорту поточні зміни узгоджуються до відкриття діалогу, імпорт створює
  новий ID лише після повної перевірки. Скасування діалогу не змінює поля,
  режим чи активний ID; успішний попередній autosave не відкочується.

Чернетка зберігається в пам'яті до прийняття/явного відкидання, не в Settings.
Аварійне завершення не гарантує її відновлення; коректно збережені дані
відновлюються з SQLite. Undo/Redo та журнал змін не додаються.

## 8. Results & Chart Behavior

Режими явно відокремлені: `demo` — демонстрація інтерфейсу, `oscillator` —
чисельний приклад RK45, пропонований `preparation` — підготовчі дані.
Перемикання зберігає блоки Parameters інших режимів, не переносить між ними
значення за схожими назвами. Для нового блока початково сім `null`.

| Стан | Панель і Canvas | Дії |
| --- | --- | --- |
| Preparation без сумісного Run | «Розрахунковий модуль ще не реалізовано»; «Немає сумісного результату для підготовчих даних», порожнє поле без вигаданих осей/серій | «Розрахувати» вимкнено з видимим поясненням; DEMO-дія прихована; CSV, cursor, legend та reset неактивні |
| Є попередній Run іншого режиму | Показати текст «Збережений запуск іншого режиму: …», ID/дату/режим; його криві не видавати за результат preparation | Запропонувати повернутися до відповідного режиму для перегляду; CSV нового режиму недоступний |
| DEMO/Oscillator після зміни входів | Зберегти попередні підсумки й криві з позначкою «Попередній запуск · параметри змінено», ID/датою/режимом | CSV експортує саме збережений Run, з явним статусом застарілості, без перерахунку |
| Run відсутній/пошкоджений/несумісної версії | Явний порожній стан або попередження про несумісність; прибрати попередній Canvas/легенду/курсор | Не створювати нульових результатів і не робити fallback до DEMO |

Параметри конфігурації та `Run.Snapshot` — незалежні знімки. Порівнювати
значення активного блока й Mode (`Run.Matches`), а не формат raw text або
UpdatedAt; зміна назви не є зміною фізичних входів. Відмінний draft позначає
в UI незбережені зміни ще до autosave. Зміни інших неактивних блоків
не роблять відповідний Run застарілим. Збереження входів не змінює
історичних Snapshot, Summary, Chart і ResultVersion, не створює новий Run.
Для `preparation` не додавати результатного типу, версії, фіктивних серій
або дозволу запуску; відхиляти прямі виклики Calculate/CreateDemo для цього Mode.

## 10. Decision Required

Лише питання, які визначають першу реалізацію. Рекомендації нижче не означають
погодження. Відкладені BAS-семантика, NC, довідники та модель результатів
не блокують запропонований редактор без обчислень і сюди не включені.

| ID / питання | Варіанти та наслідки | Рекомендація | Чому потрібне погодження |
| --- | --- | --- | --- |
| D1. Який редактор перший? | A: 7 XLS-полів, невелика форма; B: групи BAS, більший обсяг і додаткові контракти | A, окремий preparation без XLS → BAS | Вибір продуктової цілі не визначений джерелами |
| D2. Що робити з трьома Unknown units? | Уточнити до реалізації — відкласти ці поля; або дозволити числовий архів із постійним попередженням — усі 7 можна вводити без фізичного трактування | Другий варіант, без обчислень і конвертації; якщо неприйнятно — не реалізовувати їхнє введення до уточнення | Інакше UI може надати непідтвердженим значенням статус фізично перевірених |

| D4. Контракт неповних даних і чисел | Nullable binary64, кома/крапка й експонента, без вигаданих min/max — редактор архівує технічно коректні числа; або чекати повного предметного контракту — реалізація відкладається | Перший варіант, §6; Required/Default/межі лишаються Unknown | Джерела не визначають правил; треба погодити обмежені гарантії введення й точності |

## 11. Acceptance Criteria for Implementation

Це критерії наступного завдання, **не виконані runtime-перевірки Stage 6A**.

1. Погоджено D1–D5. Рівно сім предметних полів із локаторами §3; немає
   прихованого мапінгу BAS, defaults із прикладів, формульних Output у формі.
2. Три Unknown units видимі як невстановлені; одиниці інших чотирьох
   відповідають §4. Для d перевірено обидва напрями конвертації та відсутність
   накопичення похибки від render/save без редагування.
3. Кожен випадок §6 перевірено: blank/null відрізняється від 0; неповний текст,
   overflow/underflow і NaN/Infinity не змінюють збережене число. JSON round-trip
   зберігає прийняте binary64 без обіцянки точного десяткового оригіналу.
4. Debounce 450 мс і «Зберегти» використовують однакові перевірки. Перевірено
   швидке введення, запізнілу відповідь, помилку SQLite та повторне збереження;
   raw draft і нові Settings не перезаписуються старою відповіддю.
5. Перемикання/імпорт/відновлення/закриття з pending-save або некоректним
   draft виконують §7; скасування переходу/файлового діалогу зберігає редактор.
   Успіх запису не показується для новішої незбереженої ревізії.
6. Збереження/очищення входів не змінює жодного існуючого Run. Preparation
   не створює запусків; вимкнена кнопка має пояснення, прямий bridge-виклик
   не обходить заборону. Чужий результат не з'являється як сумісний графік.
7. Новою версією читаються Stage 1–4 SQLite/JSON, DEMO/Oscillator продовжують
   працювати. JSON v2 нового блока приймає null і вимагає сім ключів;
   невідомі версії/поля відхиляються. SQL-міграції та переписування історичних
   даних не потрібні. CSV старого запуску незалежний від поточних входів.
8. У native-вікнах 800×560 і 1280×800 перевірено доступність усіх полів/дій,
   розгорнуті коефіцієнти, довгі попередження, Tab, resize лівої панелі та
   читабельність робочої області. JSON/CSV, Canvas zoom/pan і робочий стан
   наявних режимів збережені; нових UI-бібліотек немає.

Для Stage 6A виконуються лише перевірка документа за джерелами,
`git status --short`, `git diff --check` і пряме форматування нового файла.
Код, тести, БД та історичні джерела не змінюються; збірки й тести не запускаються.
